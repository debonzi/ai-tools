# Canonical activation and reload

## Diagnose without mutation

Run `/db11-crew-doctor` before proposing activation or another live operation. It inspects only the canonical state root `~/.local/state/db11-crew` and reports one closed classification:

- **missing-safe:** the canonical state root is absent and may be initialized only during a later explicit activation;
- **recognized:** the exact current marker identity `db11-crew` and complete private layout are recognized at that point in time;
- **blocked:** the canonical target is unsafe or foreign and remains untouched for manual inspection.

Doctor creates no directory, marker, lock, lease, run, or Git resource. It does not inventory the Builder namespace, inspect other resource locations, authorize activation, prove ownership, or guarantee future readiness.

## Activate the exact session

Only the requester's exact image-free `/skill:db11-crew` input from Pi's direct interactive or RPC channel can request activation. Setup review, package installation, settings edits, trust, natural-language requests, extension-originated text, and another session do not activate DB11 Crew.

Activation follows this order:

1. Complete all required nonmutating session, trust, live binding, configuration, provenance, compatibility, role-resource, canonical Git discovery, and canonical-state checks.
2. Open or initialize canonical state as the first mutation.
3. Start the runtime fenced, with member and queue operations latched.
4. Persist the permanent designation for the exact current Pi session.
5. Recheck readiness, enable operations and presentation, and expose Crewlead tools.

Builder refs use only `refs/heads/db11-crew/<run-id>`. A canonical path or namespace name never proves ownership; every later mutation requires the exact durable record and fresh applicable identity, revision, fencing, repository, path, ref, and head evidence.

## Handle activation failure

A failure before canonical initialization makes no mutation. A failure after initialization or fenced startup but before designation preserves the valid current store and immutable `storeId`, stops or fences runtime resources, and leaves the session undesignated. A later activation attempt still requires a new exact requester input and repeats every check.

A failure after designation leaves one permanent marker for that exact session, keeps Crewlead tools inactive, and records the session as designated but unavailable. Repeating `/skill:db11-crew` does not retry, replace, or transfer that designation. A later session lifecycle start can recheck readiness; failure again leaves the designation and current resources unchanged.

## Reload or restore the exact same session

Request `/reload`, `/resume`, or a Pi restart separately when an installation, configuration, integration, or runtime condition must be re-evaluated. Reload is not implied by setup and does not authorize activation of another session or any integration, cleanup, rollback, or publication effect.

When the same persistent Pi session contains its exact designation, lifecycle startup restores only that session's ownership, reacquires fencing, and reconciles exact current resources. It does not append a second marker, transfer control to a new, forked, cloned, copied, different, or managed-member session, relaunch an exact existing member, or resubmit acknowledged work merely because Pi reloaded.

If readiness cannot be restored, the exact session remains designated but unavailable. Diagnose the current blocked category without repairing, adopting, deleting, renaming, or searching broadly for replacement resources.

## Preserve current resources and authority boundaries

Canonical state, designation history, durable runs and results, Builder branches and worktrees, persistent Pi sessions, and Herdr pane history survive reload and package or extension shutdown. Package removal, source reversal, rollback, terminal status, result delivery, and acknowledgement do not clean them.

Setup, reload, activation, local integration, exact runtime closure, unmerged-artifact discard, cleanup, rollback, package mutation, publication, remote access, private-service access, and destructive effects are separate authorization boundaries. Operate only on the exact current resource named by the applicable request and structured DB11 Crew operation. Secure erasure and implicit cleanup are not provided.
